## Course Description

This is the fifth studio in the BS in Enterprise AI spine. Students shift from building applications (IS 218) and understanding stakeholders (IS 265) to making those applications **survive contact with the real world** — where networks drop, processes crash, disks fill, secrets leak, and the 3 AM alert goes off.

The defining question of this studio: **"What happens when it breaks?"** Every system fails. The engineer who can diagnose, recover, and prevent recurrence is worth ten who only build happy paths. Resilience is not optimism — it is *preparation, detection, and honest response*.

Students learn to:

1. Operate in a Linux environment: processes, permissions, networking, shell scripting
2. Containerize applications with Docker and orchestrate multi-service deployments
3. Manage secrets, configuration, and authentication in production environments
4. Build observability into systems: structured logging, metrics, traces, and dashboards
5. Run incident drills, write postmortems, and design for failure

The course uses **The Phoenix Project** (Kim, Behr & Spafford) as its spine book — a narrative about an organization drowning in firefighting that learns to build resilient systems. Students see themselves in the characters and apply the lessons to their own infrastructure.

By the end of this studio, students have deployed a containerized, observable service — and have practiced what to do when it goes wrong.

## Course Learning Outcomes (Measurable)

By the end of the course, students will be able to:

1. **Navigate** a Linux environment proficiently: manage processes, set permissions, configure networking, and write shell scripts to automate operational tasks.
2. **Containerize** an application using Docker, creating reproducible builds with multi-stage Dockerfiles, managing volumes and networks, and composing multi-service deployments.
3. **Implement** secrets management, environment-based configuration, and authentication patterns appropriate for production systems.
4. **Instrument** a service with structured logging, application metrics, and request tracing, and build dashboards that surface system health.
5. **Design** for failure by identifying failure modes, implementing health checks, graceful degradation, retry logic, and circuit breakers.
6. **Execute** an incident response drill: detect a failure, diagnose root cause, recover the system, and communicate status to stakeholders.
7. **Write** a postmortem that identifies root cause, contributing factors, and specific improvement actions — without blame.
8. **Produce** a runbook documenting how to deploy, monitor, troubleshoot, and recover the system they built.

## Assessment Categories and Descriptions

**Studio Checkoffs (15%)**
Checklist-based demonstrations of:

- Linux proficiency: navigate, manage processes, set permissions, write a shell script
- Docker: build an image, run a container, use Docker Compose for multi-service setup
- Deployment: push to a cloud or hosted environment with environment variables and health check
- Observability: structured logs flowing, at least one metric dashboard, basic alerting configured

**Weekly Labs (15%)**
Hands-on technical submissions including: Linux exercises, Dockerfile creation, networking configuration, secrets management, logging integration, metrics collection, and tracing setup. Each lab builds toward the final project infrastructure.

**Midterm: Containerized Service Deployment (15%)**
A working multi-container application deployment demonstrating:

- Application container + database container (Docker Compose)
- Environment-based configuration (no hardcoded secrets)
- Health check endpoint
- Basic CI pipeline that builds and tests the containers
- README documenting how to run locally and deploy

**Final Project: Observable, Resilient Service (25%)**
A complete, containerized, deployed service with production-grade operational characteristics:

- Multi-container deployment (application + database + monitoring stack)
- Secrets management (not in code, not in plain env files)
- Authentication/authorization for service access
- Structured logging with queryable output
- Metrics collection and dashboard (e.g., Prometheus + Grafana)
- Request tracing (basic distributed tracing or correlation IDs)
- Health check endpoint with meaningful checks (DB connectivity, dependency status)
- Graceful degradation for at least one failure scenario
- Runbook: deploy, monitor, troubleshoot, recover
- Clean Git history with infrastructure-as-code

**Failure Mode Analysis — Human Edge Artifact (15%)**
A structured document identifying:

- Every way the student's system can break (network, disk, memory, dependency, data, auth, config)
- How they would detect each failure (which log, metric, alert, or symptom)
- What they would do to recover (manual steps, automated recovery, escalation)
- What they designed to prevent (health checks, retries, circuit breakers, graceful degradation)
- What they chose NOT to protect against, and why (tradeoff reasoning)

This is the Resilience Thinking artifact — evidence that the student can reason about failure systematically, not just build happy paths.

**Incident Drill + Postmortem + Demo Day (15%)**
In the final weeks, each student (or team) participates in a simulated incident:

- **Incident drill**: Instructor introduces a failure into the student's system (process killed, config corrupted, database unavailable, etc.). Student must detect, diagnose, and recover within a time window.
- **Postmortem**: Written analysis of what happened, root cause, contributing factors, timeline, and specific improvement actions. Blameless format.
- **Demo Day presentation**: Live demonstration of the system, observability dashboards, and walkthrough of the failure mode analysis. Scored on: system robustness, observability quality, communication clarity, and honest assessment of gaps.

## Responsible Use of Artificial Intelligence (Aligned to NJIT)

AI tools are useful for generating configuration snippets, debugging infrastructure issues, and explaining unfamiliar system behavior. Students are expected to use AI assistants as part of their workflow — but infrastructure is where blindly accepting AI output is **dangerous**.

Course expectations:

- Students must ensure submitted work is original and properly attributed, including AI tools and external sources.
- Students must critically evaluate and understand AI-assisted output; "the AI wrote it" is not acceptable.
- Students must comply with copyright and citation expectations.
- Students must verify all AI-generated configuration against documentation. An AI-suggested Dockerfile or security config that "looks right" but exposes secrets or fails silently is worse than no config at all.
- AI Use Notes are required for major projects describing what AI was used for, what was changed, and what was verified.

The goal: use AI to learn faster, but never trust it with your production secrets or your system's reliability.

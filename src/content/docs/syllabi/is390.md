# IS 390 — Requirements Analysis and Systems Design

**Studio label:** Systems Analysis & Design
**Credits:** 3 | **Contact hours:** 3 hrs/week | **Mode:** Studio (face-to-face)
**Human Edge capability:** Systems Thinking
**40/60 split:** Manual analysis and diagramming / AI-directed design documentation
**Prerequisites:** IS 331

<Aside type="tip" title="Position in the spine">
This is **Studio 7** — the penultimate course. Students who have built systems, operated them, and analyzed their data now learn to **see the whole picture**. IS 390 produces the blueprint that IS 425 implements.
</Aside>

---

## Course Description

This studio updates the traditional systems analysis and design course for the age of AI. Students learn to decompose complex systems — including systems with AI components that behave probabilistically — into actionable requirements, design architectures for the whole picture (performance, reliability, cost, user impact, failure modes), and produce specifications that IS 425 will implement.

The defining question: **"What emerges when the parts interact?"**

Students work with real project briefs (from the Center for Enterprise AI or industry partners): three sentences and a spreadsheet. They must go from ambiguity to a complete systems analysis package — stakeholder map, requirements with acceptance tests, architecture document, evaluation plan, and prototype.

---

## Why Systems Thinking?

AI can model systems it's trained on. It cannot notice that the system itself is the wrong frame.

Systems Thinking is the ability to see the whole when everyone else sees parts — to identify emergent behavior, unintended consequences, feedback loops, and second-order effects. Adding an AI component to a workflow doesn't just automate a step; it changes the incentives, failure modes, trust dynamics, and power relationships of the entire system. Only a human can stand back far enough to see that.

---

## Course Learning Outcomes

By the end of this course, students will be able to:

1. **Decompose** complex systems into components, interfaces, and dependencies (Analyze)
2. **Write** requirements documents with traceability to stakeholder needs and acceptance tests (Create)
3. **Design** system architectures accounting for performance, reliability, cost, and user impact (Create)
4. **Analyze** tradeoffs between competing design approaches with documented reasoning (Evaluate)
5. **Create** evaluation plans defining what "good" means, how it's measured, and what can go wrong (Create)
6. **Identify** emergent behavior and failure modes that only become visible at the system level (Analyze)
7. **Account** for AI components with probabilistic behavior in systems analysis (Analyze)
8. **Build** prototypes demonstrating key architectural decisions (Create)
9. **Construct** systems-level Context Packs including architecture constraints and tradeoff analysis (Create)

## Key Deliverables

### Systems Analysis Package (25%)
A complete blueprint for an AI-powered system that IS 425 could implement:
- **Requirements Document**: functional and non-functional requirements with traceability to stakeholder needs, acceptance tests for each requirement
- **Architecture Document**: component diagram, data flows, integration points, technology choices with tradeoff analysis
- **Risk Analysis**: failure modes, security concerns, AI-specific risks (hallucination, drift, bias), mitigation strategies
- **Evaluation Plan**: what "good" means, how it's measured, what thresholds trigger action, what can go wrong with the evaluation itself
- **Prototype**: working demonstration of key architectural decisions

### Systems Decomposition — Human Edge Artifact (15%)
A structured analysis mapping:
- How the system's components interact to produce behavior that no single component exhibits alone
- Where complexity hides — the integration points, edge cases, and failure modes that only become visible at the system level
- Feedback loops: where output becomes input, and how that changes system behavior over time
- Second-order effects: what happens when this system changes the behavior of the humans and organizations that use it
- AI-specific emergence: how probabilistic components create non-deterministic system behavior

This is the Systems Thinking artifact — evidence that the student can see the whole system, not just the parts.

### Architecture Review Presentation (15%)
Students present their architecture to a review panel (faculty + industry guests where possible), defending design decisions with evidence:
- Architecture walkthrough with tradeoff rationale
- Risk identification and mitigation strategy
- Evaluation plan defense
- Response to challenge questions
- Honest assessment of what they'd change with more time/resources

## The 40/60 Split in Practice

| Component | Hard-Way (40%) | Agentic (60%) |
|-----------|---------------|---------------|
| Requirements | Face-to-face stakeholder negotiation; hand-drawn process maps | AI-assisted requirements organization; traceability matrix generation |
| Architecture | Hand-drawn component diagrams; manual tradeoff tables | AI-directed architecture documentation; alternative generation |
| Evaluation | Manual metric selection; hand-calculated baselines | AI-assisted evaluation framework; automated test generation |
| Prototyping | Manual implementation of critical path | AI-directed prototype generation; rapid iteration |

## How IS 390 Feeds IS 425

IS 390 and IS 425 form a **design → build** pair:

| IS 390 Produces | IS 425 Implements |
|-----------------|-------------------|
| Requirements document | Working system matching requirements |
| Architecture blueprint | Production deployment following architecture |
| Evaluation plan | Evaluation harness with regression gates |
| Risk analysis | Observability and mitigation in production |
| Prototype | Full implementation with client delivery |

Teams that form in IS 390 may continue into IS 425 (where possible), providing continuity from analysis to implementation. The IS 390 Systems Analysis Package becomes the starting Context Pack for IS 425.

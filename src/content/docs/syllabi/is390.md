## Course Description

This studio updates the traditional systems analysis and design course for the age of AI. Students learn to decompose complex systems — including systems with AI components that behave probabilistically — into actionable requirements, design architectures that account for the whole picture (performance, reliability, cost, user impact, failure modes), and produce specifications that IS 425 will implement.

The defining question: **"What emerges when the parts interact?"**

Students work with real project briefs (from the Center for Enterprise AI or industry partners): three sentences and a spreadsheet. They must go from ambiguity to a complete systems analysis package — stakeholder map, requirements with acceptance tests, architecture document, evaluation plan, and prototype.

## The Stories Behind the Technology

Systems thinking has its own pantheon — people who saw the whole when everyone else saw parts:

- **Grady Booch** is one of the inventors of the **Unified Modeling Language (UML)** and a pioneer of object-oriented design. His core insight: complex systems can only be understood through multiple views — no single diagram captures the whole truth. A class diagram shows structure but not behavior. A sequence diagram shows interaction but not deployment. You need all the views, held together by an architect who understands which view answers which question. Booch also co-created the **Rational Unified Process** and later joined IBM Research to work on AI architecture. His career is a lesson in Systems Thinking: the ability to zoom in on components and zoom out to see the whole.
- **Donella Meadows** was an environmental scientist and systems theorist who wrote *Thinking in Systems: A Primer* (2008, published posthumously). Her key framework: **leverage points** — the places in a system where a small change produces a big effect. Most people push the easy levers (add more resources, add more rules). The most powerful levers are the hardest to find: the goals of the system, the paradigm out of which the system arises, the power to transcend paradigms. When you analyze an AI system, Meadows's framework helps you find where a design change will actually matter.
- **Fred Brooks** (again — because his ideas span the whole spine) identified the **"second-system effect"**: the tendency to over-design your second system by cramming in all the features you left out of the first. IS 390 students are designing systems after five studios of experience. The temptation to over-engineer is real. Brooks's warning: elegance is not additional features. It's the minimum set of features that fully solves the problem.
- **Jay Forrester** invented **system dynamics** at MIT in the 1950s — the mathematical framework for modeling feedback loops, delays, and nonlinear behavior in complex systems. His models of urban dynamics and global resource limits (the "Limits to Growth" study) showed that systems often behave counterintuitively: the obvious solution makes things worse because it ignores feedback loops. Every AI system has feedback loops (user behavior changes the training data changes the model changes the user behavior). Forrester's work explains why.

## Foundations: The Mathematics of Systems

Systems analysis requires mathematical thinking applied to architecture:

- **Graph theory for architecture**: System architectures are graphs — components are nodes, dependencies are edges. Cycle detection reveals circular dependencies. Topological sort reveals build and deployment order. Degree centrality reveals which components are most critical (and most risky).
- **Probability for AI components**: AI components don't always give the same answer. Understanding accuracy, precision, recall, F1 — and what each metric hides — is essential for specifying AI component requirements. If your system requires 95% accuracy, what does that mean for the 5% of users who get wrong answers?
- **Queuing theory for performance**: Request arrival rates, service times, queue depths. Little's Law (L = lambda * W) tells you how many requests are in your system at any moment. These are the numbers that drive architecture decisions about scaling, caching, and load balancing.
- **Decision matrices**: Weighted scoring for architecture tradeoffs — assign criteria (performance, cost, reliability, time-to-market), weight each criterion, score each option. This is basic linear algebra applied to design decisions. The math is simple; the judgment about weights is where the real thinking happens.

## Security at the Architecture Level

IS 390 introduces security as a first-class architectural concern, not an afterthought:

- **Threat modeling**: STRIDE (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) applied to every component in the architecture
- **Attack surface analysis**: Every interface, endpoint, and data flow is a potential attack vector. Architecture decisions expand or reduce the attack surface.
- **Defense in depth**: Multiple layers of security controls so that no single failure compromises the system. This is systems thinking applied to security — no single component can be trusted to be secure.
- **AI-specific security**: Model extraction attacks, prompt injection, data poisoning, adversarial inputs. When your architecture includes AI components, the threat model must include AI-specific threats.
- **Zero Trust architecture**: The principle that no component, user, or network connection is trusted by default. Every access must be verified. This is increasingly the standard for enterprise systems.

## The Entrepreneurial Lens on Systems

IS 390 connects systems design to business reality:

- **Build vs. buy vs. open-source**: For every component in the architecture, the decision isn't just technical — it's strategic. What's your core differentiator? Build that. What's commodity? Buy it. What's well-solved by the community? Use open-source. This is Lean thinking applied to architecture.
- **Technical debt as strategic choice**: Sometimes you deliberately take on debt (use a simpler architecture now, plan to refactor later) because time-to-market matters more than elegance. The key is being explicit: this is debt, here's the interest rate, here's when we'll pay it off.
- **Platform thinking**: Does this system serve one client or many? The difference between a bespoke solution and a platform has enormous architectural implications. Amazon's origin as a bookstore and evolution into AWS is the ultimate platform thinking example.

## Why Systems Thinking?

AI can model systems it's trained on. It cannot notice that the system itself is the wrong frame.

Systems Thinking is the ability to see the whole when everyone else sees parts — to identify emergent behavior, unintended consequences, feedback loops, and second-order effects. Adding an AI component to a workflow doesn't just automate a step; it changes the incentives, failure modes, trust dynamics, and power relationships of the entire system. Only a human can stand back far enough to see that.

## Course Learning Outcomes

By the end of this course, students will be able to:

1. **Decompose** complex systems into components, interfaces, and dependencies (Analyze)
2. **Write** requirements documents with traceability to stakeholder needs and acceptance tests (Create)
3. **Design** system architectures accounting for performance, reliability, cost, security, and user impact (Create)
4. **Analyze** tradeoffs between competing design approaches using decision matrices and documented reasoning (Evaluate)
5. **Create** evaluation plans defining what "good" means, how it's measured, and what can go wrong (Create)
6. **Identify** emergent behavior and failure modes that only become visible at the system level (Analyze)
7. **Conduct** threat modeling for systems that include AI components with probabilistic behavior (Analyze)
8. **Build** prototypes demonstrating key architectural decisions (Create)
9. **Construct** systems-level Context Packs including architecture constraints, threat models, and tradeoff analysis (Create)

## Assessment

### AI-Generated Vocabulary Quizzes (30%)

Weekly quizzes covering systems analysis, architecture, and security concepts:

- Architecture patterns (monolith, microservices, event-driven, pipeline, layered)
- Requirements engineering (traceability, acceptance criteria, NFRs)
- Systems thinking vocabulary (emergence, feedback loops, leverage points, delays)
- Security (STRIDE, defense in depth, Zero Trust, attack surface, threat modeling)
- UML and modeling concepts (component diagrams, sequence diagrams, deployment diagrams)
- Probability and metrics for AI component specification
- Concepts from Meadows and Booch readings

### Qualitative Studio Reviews (70%)

| Review Point | What's Evaluated |
|---|---|
| **Week 4 — Requirements + Stakeholder Review** | Stakeholder map, requirements document with acceptance tests, initial threat model. Can the student explain traceability — how each requirement connects to a stakeholder need? |
| **Week 8 — Midterm: Architecture + Tradeoff Review** | Architecture document with component diagram, tradeoff analysis using decision matrix, initial threat model. Can the student defend why this architecture over alternatives? Can they identify feedback loops? |
| **Week 12 — Prototype + Evaluation Review** | Working prototype demonstrating key decisions, evaluation plan, complete threat model. Can the student explain what emergence means in their specific system — what behavior appears only when components interact? |
| **Week 15 — Final Studio Review: Architecture Review Day** | Complete Systems Analysis Package presented to a review panel. Can the student explain failure modes, security posture, and what they'd change with more time? |

Each review documents: what the student demonstrated, feedback given, commitments for improvement, qualitative rating (Exceeds / Meets / Approaching / Not Yet).

**Letter Grade Scale:** A: 90–100 | B+: 86–89 | B: 80–85 | C+: 76–79 | C: 70–75 | D: 60–69 | F: 0–59

*Final grades combine quiz scores (30%) and the instructor's holistic assessment across the four studio reviews (70%).*

## Key Deliverables

### Systems Analysis Package (final project)
A complete blueprint for an AI-powered system that IS 425 could implement:
- **Requirements Document**: functional and non-functional requirements with traceability to stakeholder needs, acceptance tests for each requirement
- **Architecture Document**: component diagram, data flows, integration points, technology choices with decision matrix and tradeoff analysis
- **Threat Model**: STRIDE analysis, attack surface map, security controls with defense-in-depth rationale
- **Risk Analysis**: failure modes, AI-specific risks (hallucination, drift, bias), mitigation strategies
- **Evaluation Plan**: what "good" means, how it's measured, what thresholds trigger action, what can go wrong with the evaluation itself
- **Prototype**: working demonstration of key architectural decisions

### Systems Decomposition — Human Edge Artifact
A structured analysis mapping:
- How the system's components interact to produce behavior no single component exhibits alone
- Where complexity hides — integration points, edge cases, failure modes visible only at the system level
- Feedback loops: where output becomes input, and how that changes system behavior over time
- Second-order effects: what happens when this system changes the behavior of the humans and organizations that use it
- AI-specific emergence: how probabilistic components create non-deterministic system behavior
- Leverage points: where a small design change produces the biggest improvement (Meadows framework)

### Architecture Review Day (Week 15)
Students present their architecture to a review panel (faculty + industry guests where possible), defending design decisions with evidence:
- Architecture walkthrough with tradeoff rationale
- Threat model and security posture defense
- Evaluation plan defense
- Response to challenge questions
- Honest assessment of what they'd change with more time/resources

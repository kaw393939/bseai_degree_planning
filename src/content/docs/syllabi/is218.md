## Course Description

Students take the application engineering skills from IS 118 and confront the hardest problem in software: **keeping systems running when the world is trying to break them.** They learn containerization, deployment pipelines, infrastructure-as-code, logging, monitoring, alerting, and incident response — not as abstract topics but by operating a real system under real failure conditions.

The defining question: **"What happens when this fails — and what do we do about it?"**

The instructor introduces failures. Infrastructure goes down. Dependencies break. Load spikes. Students must detect the problem, diagnose the root cause, restore service, and write an honest postmortem. This is Resilience Thinking in practice: not preventing failure (impossible) but building systems — and people — that recover well.

## The Stories Behind the Technology

The tools of production engineering were forged in real crises by people who refused to accept fragile systems:

- **Linus Torvalds** didn't just create Git — he created **Linux** (1991), starting as a Finnish student who posted "I'm doing a (free) operating system (just a hobby, won't be big and professional)" to a Usenet group. Linux now runs 96% of the world's top million web servers, every Android phone, and most of the cloud. The lesson: open-source collaboration at scale requires both brilliant architecture and resilience to thousands of contributors breaking things.
- **Robert C. "Uncle Bob" Martin** spent decades watching software projects fail and distilled what he learned into *Clean Code* (2008) and the **SOLID principles**. His central argument: code that's hard to read is hard to fix, and code that's hard to fix is fragile. "The ratio of time spent reading code to writing code is 10:1." Every line of clean code is a resilience investment.
- **Solomon Hykes** created **Docker** in 2013 because deploying applications was a nightmare of "it works on my machine" problems. Containers solved this by packaging applications with their dependencies. The container revolution made deployment reproducible — and made this course possible.
- **The Agile Manifesto** (2001): Seventeen developers at Snowbird, Utah — including Uncle Bob Martin, Kent Beck, Ward Cunningham, and Martin Fowler — wrote four values and twelve principles that changed software development. They were frustrated by heavyweight processes that produced documentation instead of working software. The Manifesto's core insight: you cannot plan your way out of uncertainty. You must build, ship, learn, and adapt. This is resilience thinking applied to process.
- **Kent Beck** invented **Test-Driven Development** and **Extreme Programming** — both born from the conviction that the best way to build reliable software is to write the test first, then write the code that makes it pass. TDD is a resilience practice: every test is a contract that prevents future breakage.

## The Twelve-Factor App: A Manifesto for Production Software

In 2011, **Adam Wiggins** and the team at **Heroku** had a front-row seat to a phenomenon nobody had seen before. Heroku was one of the first platform-as-a-service companies — developers pushed code, and Heroku ran it in the cloud. They watched thousands of applications deploy. Some thrived. Some broke in spectacular ways. And the patterns were consistent: the apps that survived at scale shared specific architectural properties, and the apps that collapsed shared specific architectural mistakes.

Wiggins codified what they learned into **The Twelve-Factor App** — a manifesto for building software that works in production:

1. **Codebase** — One codebase, tracked in version control, many deploys
2. **Dependencies** — Explicitly declare and isolate dependencies
3. **Config** — Store config in the environment (not in code)
4. **Backing services** — Treat databases, caches, queues as attached resources
5. **Build, release, run** — Strictly separate build and run stages
6. **Processes** — Execute the app as stateless processes
7. **Port binding** — Export services via port binding
8. **Concurrency** — Scale out via the process model
9. **Disposability** — Maximize robustness with fast startup and graceful shutdown
10. **Dev/prod parity** — Keep development, staging, and production as similar as possible
11. **Logs** — Treat logs as event streams
12. **Admin processes** — Run admin/management tasks as one-off processes

These aren't abstract principles — they're **survival lessons from production.** Factor 3 (config in environment) prevents the disaster where a developer accidentally pushes database credentials to GitHub. Factor 9 (disposability) means your container can be killed and restarted without losing data or corrupting state. Factor 10 (dev/prod parity) prevents the classic "it works on my machine" (because your machine *is* production, architecturally).

IS 218 uses the Twelve-Factor App as a scorecard. By semester's end, students can evaluate any application against all twelve factors and explain what breaks when you violate each one.

## Design Pattern Vocabulary: The Gang of Four

In 1994, four computer scientists — **Erich Gamma, Richard Helm, Ralph Johnson, and John Vlissides** — published *Design Patterns: Elements of Reusable Object-Oriented Software*. The book catalogued 23 recurring solutions to common software design problems. The authors became known as the **Gang of Four (GoF)**, and their book became the most influential software engineering text of the 1990s.

But the GoF book's lasting impact isn't the patterns themselves — it's the **vocabulary** they created.

Before the GoF, two developers solving the same problem might arrive at an identical architecture and have no shared way to discuss it. After the GoF, you could say "Observer pattern" and every professional developer in the room knew you meant a one-to-many dependency where an object notifies its dependents of state changes. You could say "Strategy pattern" and everyone understood you meant encapsulating algorithms behind an interface so they're interchangeable. You could say "Singleton" and immediately trigger a productive argument about whether that's ever a good idea.

**Design patterns are the professional vocabulary of software architecture.** Knowing them doesn't make you a better coder — but it makes you a better communicator, a better team member, and a better reader of other people's code. When you join a team and the tech lead says "we use the Repository pattern for data access and the Observer pattern for event handling," you need to know what that means. When you're reviewing AI-generated code, recognizing which pattern it's implementing (or mangling) is a core Professional Judgment skill.

IS 218 covers the most commonly used patterns in web application engineering:

| Pattern | What it solves | Where you see it in IS 218 |
|---------|---------------|---------------------------|
| **Observer** | Decoupling event producers from consumers | Monitoring: metrics emit events that dashboards and alerts consume independently |
| **Strategy** | Swapping algorithms without changing the caller | Deployment: blue-green vs. canary vs. rolling are interchangeable deployment strategies |
| **Factory** | Creating objects without specifying exact classes | Container orchestration: Docker creates containers from images without the app knowing the infrastructure |
| **Decorator** | Adding behavior to objects without modifying them | Middleware: logging, authentication, and rate limiting wrap your API handlers |
| **Proxy** | Controlling access to an object | Reverse proxies (Nginx): sitting between the client and your application, handling SSL, caching, load balancing |
| **Singleton** | Ensuring only one instance exists | Database connection pools: one pool shared across the application (and why global state is usually a bad idea) |

Students don't memorize all 23 patterns. They learn to **speak the language** — to recognize patterns in the systems they build and operate, to name them correctly, and to discuss architecture using the shared vocabulary that professional software engineers expect.

## Foundations: The Mathematics of Reliability

Production systems live or die by numbers. IS 218 builds mathematical intuition through practical problems:

- **Uptime and nines**: What does "99.9% uptime" actually mean? (8.76 hours of downtime per year.) What about 99.99%? (52 minutes.) The difference between three nines and four nines is the difference between a hobby project and an enterprise system. This is percentage math applied to real stakes.
- **Latency percentiles**: Mean response time lies to you. P50, P95, P99 tell different stories. Understanding percentiles means understanding distributions — statistics applied to system performance.
- **Load and capacity**: If your server handles 100 requests/second and you get 150, what happens? Queuing theory basics: arrival rate vs. service rate, Little's Law, why systems fall off a cliff at saturation.
- **Error budgets**: Google's SRE practice of quantifying acceptable failure. If your SLA is 99.9%, you have an error budget of 0.1% — about 43 minutes/month. When you've spent your budget, you stop shipping features and fix reliability. This is risk math applied to engineering decisions.

## The Lean Engineering Mindset

IS 218 deepens the entrepreneurial thinking from IS 118 by applying Lean principles to engineering:

- **Eliminate waste**: Every manual deployment step, every unmonitored endpoint, every untested code path is waste. Lean thinking (from Toyota's production system) applied to software means automating everything that can be automated — and being ruthlessly honest about what can't.
- **Continuous improvement (Kaizen)**: Postmortems are not punishment. They are kaizen — structured reflection on what went wrong and how to prevent it next time. This is the Agile principle of regular retrospection applied to operations.
- **Flow over batch**: CI/CD is Lean applied to software delivery — small, frequent changes that flow through the pipeline instead of big, scary releases that batch up risk.

## Why Resilience Thinking?

AI can write deployment scripts, generate monitoring dashboards, and even suggest fixes for common errors. It cannot decide what matters when everything is on fire.

Resilience Thinking is the ability to function under pressure, prioritize when multiple things fail simultaneously, communicate honestly when you don't yet know the root cause, and most importantly — to design systems that degrade gracefully rather than catastrophically. It's not about preventing failure. It's about failing well.

8. **Identify** and name common design patterns (GoF) in production code and explain their role in system architecture (Analyze)

10. **Execute** an Incident Drill: detect, diagnose, mitigate, communicate, and recover from an injected failure (Apply)
11. **Construct** a Context Pack documenting infrastructure decisions, failure modes, and operational procedures (Create)

## How the Studio Works: The Coaching Model

IS 218 — like every studio in the spine — operates on a coaching philosophy, not a lecture-and-exam model. The instructors are **coaches and facilitators** whose job is to meet students where they are, treat them as whole people, and create an environment where transformation happens through doing.

**The weekly rhythm:**

Every week has the same structure, creating a reliable beat that students can count on:

1. **Canvas Quiz** (before class, auto-graded) — A short vocabulary and concept quiz covering the week's topic. Takes 10-15 minutes. Delivered and graded automatically through Canvas. These build the shared professional vocabulary (12-Factor, GoF patterns, reliability concepts, security terms) and verify engagement with the material. Not tricky — if you did the reading and paid attention last week, you pass.

2. **Studio Session** (in class) — The instructor introduces the week's concept with a story and a demonstration, then students work. Hands on keyboards. Peer feedback sessions using the CRC critique method from IS 117. The instructor circulates, coaches, troubleshoots, and gives real-time feedback. **The goal is to get people talking, building, and helping each other.**

3. **Peer Critique** (in class, pass/fail) — Students give and receive structured feedback on each other's work. This is documented and graded pass/fail: you showed up, you participated, you gave constructive feedback. This is the accountability mechanism and the social glue.

**The design intent:** Passing is achievable for anyone who shows up and engages. The quizzes reward consistency. The critiques reward presence and participation. The distinction between good and great happens at Demo Day and the final project, where the instructor panel scores work quantitatively. The A goes to students whose work is genuinely excellent — visibly, measurably, defended in front of peers and faculty.

**Why this works:** Students who feel safe and supported take bigger risks, ask better questions, and produce better work. The studio is not a filter designed to fail people. It's a gym designed to make people stronger. The instructor is the coach who pushes you further than you'd push yourself — but who also spots you when the weight gets heavy.

## Assessment

Assessment is designed to reward engagement and effort while reserving top grades for demonstrated excellence. The structure ensures that **consistent participation guarantees a passing grade**, while the A requires work that impresses a panel of faculty evaluators.

### Weekly Canvas Quizzes — 20%
- ~12 quizzes across the semester, auto-graded through Canvas
- Cover vocabulary, concepts, and foundational knowledge: 12-Factor App principles, GoF pattern names and purposes, Clean Code principles, monitoring terminology, security vocabulary, reliability math
- Multiple choice, matching, short answer — objective and auto-graded
- Lowest 2 scores dropped
- **Design intent:** These are easy points for engaged students. They build the professional vocabulary you need to speak the language of production engineering. If you do the reading and attend class, you'll score well.

### Studio Participation and Peer Critiques — 30%
- Graded **pass/fail per session** (~14 sessions)
- Criteria: present, engaged, gave CRC feedback to peers, participated in discussion
- Documented by the instructor at each session
- Up to 2 absences without penalty
- **Design intent:** This is the attendance and engagement mechanism. It's what gets people into the room, talking to each other, building the social climate that makes a studio work. Pass/fail means nobody agonizes over critique grades — but missing sessions costs real points.

### Final Project + Demo Day — 50%
- The production system built across the semester, evaluated at Demo Day (Week 15)
- **Scored by an instructor panel** (all studio instructors participate): each evaluator scores independently using a shared rubric, scores are aggregated
- Rubric categories:
  - **Technical completeness**: Does it meet the 12-Factor criteria? Is it containerized, monitored, tested, deployed?
  - **Resilience evidence**: Failure Mode Analysis quality, incident response capability, postmortem depth
  - **Code quality**: Clean Code evidence, pattern usage, readability
  - **Defense quality**: Can the student explain every decision? Do they handle tough questions with honesty?
  - **Security posture**: Are production security practices in evidence?
- **Design intent:** This is where grade differentiation happens. A student who shows up every week and builds a functional but basic system earns a solid B. A student whose system is well-architected, thoroughly tested, clearly documented, and confidently defended earns the A.

**Letter Grade Scale:** A: 90-100 | B+: 86-89 | B: 80-85 | C+: 76-79 | C: 70-75 | D: 60-69 | F: 0-59

**How the math works:**
- A student who completes all quizzes (18/20), attends all sessions (30/30), and builds a competent project (35/50) earns an **83 (B)** — a solid grade for solid effort.
- A student who aces the quizzes (20/20), attends all sessions (30/30), and delivers outstanding work scored highly by the panel (45/50) earns a **95 (A)**.
- A student who does the quizzes (15/20) and attends most sessions (25/30) but delivers a minimal project (25/50) earns a **65 (D)** — the signal that more effort on the project is needed.
- **The floor for an engaged student is a passing grade. The ceiling is earned through excellent work.**

## Signature Assessments

### Failure Mode Analysis (FMA)
A systematic mapping of every way the system can fail:
- Component failures: what happens when the database goes down? The API? The auth service?
- Dependency failures: what happens when a third-party service is unreachable?
- Data failures: what happens when data is corrupted, stale, or missing?
- Security failures: what happens when credentials leak? When a container is compromised?
- User impact: for each failure mode, what does the user experience?
- Mitigation: for each failure mode, what prevents it, detects it, or limits its blast radius?
- 12-Factor evaluation: which factors prevent which failure modes?

### Incident Drill
The instructor injects a realistic failure (infrastructure outage, data corruption, security incident). Students must:
1. **Detect**: notice something is wrong, using monitoring or alerts
2. **Diagnose**: systematically narrow the root cause
3. **Mitigate**: restore service (even if degraded)
4. **Communicate**: update stakeholders honestly ("we don't know yet" is acceptable; silence is not)
5. **Recover**: full restoration and verification
6. **Postmortem**: blameless analysis of what happened, why, and how to prevent recurrence

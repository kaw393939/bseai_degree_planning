## Course Description

Students take the application engineering skills from IS 118 and confront the hardest problem in software: **keeping systems running when the world is trying to break them.** They learn containerization, deployment pipelines, infrastructure-as-code, logging, monitoring, alerting, and incident response — not as abstract topics but by operating a real system under real failure conditions.

The defining question: **"What happens when this fails — and what do we do about it?"**

The instructor introduces failures. Infrastructure goes down. Dependencies break. Load spikes. Students must detect the problem, diagnose the root cause, restore service, and write an honest postmortem. This is Resilience Thinking in practice: not preventing failure (impossible) but building systems — and people — that recover well.

## The Stories Behind the Technology

The tools of production engineering were forged in real crises by people who refused to accept fragile systems:

- **Linus Torvalds** didn't just create Git — he created **Linux** (1991), starting as a Finnish student who posted "I'm doing a (free) operating system (just a hobby, won't be big and professional)" to a Usenet group. Linux now runs 96% of the world's top million web servers, every Android phone, and most of the cloud. The lesson: open-source collaboration at scale requires both brilliant architecture and resilience to thousands of contributors breaking things.
- **Robert C. "Uncle Bob" Martin** spent decades watching software projects fail and distilled what he learned into *Clean Code* (2008) and the **SOLID principles**. His central argument: code that's hard to read is hard to fix, and code that's hard to fix is fragile. "The ratio of time spent reading code to writing code is 10:1." Every line of clean code is a resilience investment.
- **Solomon Hykes** created **Docker** in 2013 because deploying applications was a nightmare of "it works on my machine" problems. Containers solved this by packaging applications with their dependencies. The container revolution made deployment reproducible — and made this course possible.
- **The Agile Manifesto** (2001): Seventeen developers at Snowbird, Utah — including Uncle Bob Martin, Kent Beck, Ward Cunningham, and Martin Fowler — wrote four values and twelve principles that changed software development. They were frustrated by heavyweight processes that produced documentation instead of working software. The Manifesto's core insight: you cannot plan your way out of uncertainty. You must build, ship, learn, and adapt. This is resilience thinking applied to process.
- **Kent Beck** invented **Test-Driven Development** and **Extreme Programming** — both born from the conviction that the best way to build reliable software is to write the test first, then write the code that makes it pass. TDD is a resilience practice: every test is a contract that prevents future breakage.

## Foundations: The Mathematics of Reliability

Production systems live or die by numbers. IS 218 builds mathematical intuition through practical problems:

- **Uptime and nines**: What does "99.9% uptime" actually mean? (8.76 hours of downtime per year.) What about 99.99%? (52 minutes.) The difference between three nines and four nines is the difference between a hobby project and an enterprise system. This is percentage math applied to real stakes.
- **Latency percentiles**: Mean response time lies to you. P50, P95, P99 tell different stories. Understanding percentiles means understanding distributions — statistics applied to system performance.
- **Load and capacity**: If your server handles 100 requests/second and you get 150, what happens? Queuing theory basics: arrival rate vs. service rate, Little's Law, why systems fall off a cliff at saturation.
- **Error budgets**: Google's SRE practice of quantifying acceptable failure. If your SLA is 99.9%, you have an error budget of 0.1% — about 43 minutes/month. When you've spent your budget, you stop shipping features and fix reliability. This is risk math applied to engineering decisions.

## The Lean Engineering Mindset

IS 218 deepens the entrepreneurial thinking from IS 118 by applying Lean principles to engineering:

- **Eliminate waste**: Every manual deployment step, every unmonitored endpoint, every untested code path is waste. Lean thinking (from Toyota's production system) applied to software means automating everything that can be automated — and being ruthlessly honest about what can't.
- **Continuous improvement (Kaizen)**: Postmortems are not punishment. They are kaizen — structured reflection on what went wrong and how to prevent it next time. This is the Agile principle of regular retrospection applied to operations.
- **Flow over batch**: CI/CD is Lean applied to software delivery — small, frequent changes that flow through the pipeline instead of big, scary releases that batch up risk.

## Why Resilience Thinking?

AI can write deployment scripts, generate monitoring dashboards, and even suggest fixes for common errors. It cannot decide what matters when everything is on fire.

Resilience Thinking is the ability to function under pressure, prioritize when multiple things fail simultaneously, communicate honestly when you don't yet know the root cause, and most importantly — to design systems that degrade gracefully rather than catastrophically. It's not about preventing failure. It's about failing well.

## Course Learning Outcomes

By the end of this course, students will be able to:

1. **Containerize** applications using Docker and manage multi-service deployments with Docker Compose (Apply)
2. **Build** CI/CD pipelines that automate testing, building, and deployment (Create)
3. **Implement** structured logging, metrics collection, and alerting for production systems (Create)
4. **Diagnose** production failures using logs, metrics, and systematic debugging (Analyze)
5. **Write** blameless postmortems with root cause analysis and concrete prevention steps (Evaluate)
6. **Apply** security best practices: secrets management, container security, dependency scanning, OWASP awareness (Apply)
7. **Conduct** the Failure Mode Analysis — mapping every way a system can fail and what happens to users when it does (Analyze)
8. **Execute** an Incident Drill: detect, diagnose, mitigate, communicate, and recover from an injected failure (Apply)
9. **Construct** a Context Pack documenting infrastructure decisions, failure modes, and operational procedures (Create)

### Qualitative Studio Reviews (70%)

| Review Point | What's Evaluated |
|---|---|
| **Week 4 — Container + Pipeline Review** | Working containerized app with CI/CD pipeline. Can the student explain what happens at each pipeline stage and why? Can they calculate uptime percentiles? |
| **Week 8 — Monitoring + Observability Review** | Structured logging, dashboards, alerts. Can the student explain what each metric means and what action to take when it goes red? Failure Mode Analysis draft. |

Each review is a **conversation** between instructor and student, documented with:
- What the student demonstrated
- Feedback given (including technical and judgment-related)
- Commitments for improvement
- Qualitative rating: Exceeds / Meets / Approaching / Not Yet

**Letter Grade Scale:** A: 90–100 | B+: 86–89 | B: 80–85 | C+: 76–79 | C: 70–75 | D: 60–69 | F: 0–59

*Final grades combine quiz scores (30%) and the instructor's holistic assessment across the four studio reviews (70%).*

## Signature Assessments

### Failure Mode Analysis (FMA)
A systematic mapping of every way the system can fail:
- Component failures: what happens when the database goes down? The API? The auth service?
- Dependency failures: what happens when a third-party service is unreachable?
- Data failures: what happens when data is corrupted, stale, or missing?
- Security failures: what happens when credentials leak? When a container is compromised?
- User impact: for each failure mode, what does the user experience?
- Mitigation: for each failure mode, what prevents it, detects it, or limits its blast radius?

### Incident Drill
The instructor injects a realistic failure (infrastructure outage, data corruption, security incident). Students must:
1. **Detect**: notice something is wrong, using monitoring or alerts
2. **Diagnose**: systematically narrow the root cause
3. **Mitigate**: restore service (even if degraded)
4. **Communicate**: update stakeholders honestly ("we don't know yet" is acceptable; silence is not)
5. **Recover**: full restoration and verification
6. **Postmortem**: blameless analysis of what happened, why, and how to prevent recurrence

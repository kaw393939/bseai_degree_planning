## Course Description

Students build a real product — a **workshop registration system** for the Center for Enterprise AI — using JavaScript, server-side fundamentals, databases, APIs, and automated testing. This is not an abstract exercise. The system must handle user registration, session management, capacity limits, confirmation emails, and an admin dashboard. Real people will use it.

Along the way, students confront the central question of Professional Judgment: **"Just because AI can generate this code, should I ship it?"**

The answer requires understanding what the code does, what could go wrong, who gets hurt when it fails, and whether you'd stake your name on it. That's judgment — and no AI has it.

## The Stories Behind the Technology

Every tool you use was built by someone who had a better idea — or a deep frustration:

- **Brendan Eich** created JavaScript in ten days at Netscape in 1995. It was originally called Mocha, then LiveScript, then JavaScript (for marketing reasons — Java was hot). Twenty-nine years later, it's the most widely used programming language on Earth. The lesson: tools built under pressure can still change the world, but they accumulate "technical debt" — a term coined by **Ward Cunningham**, who also invented the first wiki.
- **Ward Cunningham** compared quick-and-dirty code to financial debt: you can ship faster now, but you'll pay interest later. Every shortcut in your workshop registration system is a debt you'll either repay or pass on to a future developer.
- **Roy Fielding** defined REST in his 2000 PhD dissertation — the architectural style that makes modern web APIs work. When your front end talks to your back end, it speaks REST (or something inspired by it). Fielding didn't just describe how the web works; he explained *why* it works.
- **The Pragmatic Programmer** — Andy Hunt and Dave Thomas wrote this book in 1999, arguing that programming is a craft, not just a job. Their advice: "Don't live with broken windows." Fix the small things before they become big things. This is Professional Judgment in practice.

## Foundations: Building with Numbers

IS 118 continues the foundational knowledge thread from IS 117, now applied to real programming:

- **How JavaScript handles numbers**: IEEE 754 floating point — why `0.1 + 0.2 !== 0.3` and what that means for handling money in your registration system. When to use integers (cents, not dollars).
- **The calculator as architecture teacher**: Students build a calculator app at the start of the course — not because calculators are exciting, but because a calculator forces you to think about state management, input validation, edge cases (divide by zero, overflow), and the gap between "it works for me" and "it works for everyone." A calculator is a tiny application with all the architectural problems of a large one.
- **Boolean logic and conditionals**: How true/false, AND/OR/NOT map to real decisions in your code and to real gatekeeping in your application (can this user register? is this session full?).
- **Data representation in practice**: JSON, form data, query strings — how information moves between browser and server, and why getting the format wrong causes silent failures.

## The Entrepreneurial Mindset

The workshop registration system is not just a coding exercise — it's a **product**. IS 118 introduces the entrepreneurial thinking that runs through the rest of the program:

- **Who is the user?** Center staff managing events. Attendees registering. Instructors checking rosters. Each has different needs, and you can't build for all of them at once.
- **Minimum Viable Product (MVP)**: What's the smallest thing you can ship that actually works? Eric Ries's *Lean Startup* principle: build, measure, learn. Don't build features nobody asked for.
- **The Agile Manifesto** (2001): Seventeen software developers met at a ski lodge in Utah and wrote four values that changed how software gets built — individuals over processes, working software over documentation, customer collaboration over contract negotiation, responding to change over following a plan. Students learn these values by living them in the studio.
- **User stories over feature lists**: "As a workshop attendee, I want to see available sessions so I can register for one" is a better requirement than "implement session listing." This is how real products get built.

## Why Professional Judgment?

AI can generate a login form, a database query, a test suite. It cannot know whether the login form leaks user data, whether the query will scale under load, or whether the test covers the case that will actually break in production.

Professional Judgment is the capacity to look at technically correct output and decide: is this *good enough to ship*? Does it handle edge cases? Does it fail gracefully? Would I want my name on it? In IS 118, students develop this judgment by building something real — where "it works on my machine" is not an acceptable standard.

## Course Learning Outcomes

By the end of this course, students will be able to:

1. **Build** a full-stack web application with front-end UI, server-side logic, and database persistence (Create)
2. **Write** automated tests — unit, integration, and end-to-end — and explain what each level catches (Create)
3. **Implement** user authentication and session management with awareness of security implications (Apply)
4. **Design** RESTful APIs that follow conventions and handle errors gracefully (Create)
5. **Evaluate** AI-generated code against quality criteria: correctness, security, readability, maintainability (Evaluate)
6. **Set up** CI/CD pipelines that run tests automatically on every push (Apply)
7. **Produce** the AI Audit Log — a documented record of every AI interaction, what was accepted, what was modified, and why (Create)
8. **Explain** foundational concepts: floating-point arithmetic, boolean logic, state management, data serialization (Understand)
9. **Construct** a Context Pack documenting architectural decisions, quality criteria, and known limitations (Create)

## Assessment

### AI-Generated Vocabulary Quizzes (30%)

Weekly quizzes covering programming concepts, security terminology, and software craft principles:

- JavaScript fundamentals (scope, closures, async/await, event loop)
- Database concepts (schema, normalization, SQL basics, ACID)
- Security vocabulary (authentication vs. authorization, XSS, CSRF, SQL injection)
- Software engineering principles (DRY, technical debt, separation of concerns)
- Concepts from *The Pragmatic Programmer* reading assignments

Quizzes are generated by AI and reviewed by the instructor. They verify engagement with the material and build a shared professional vocabulary.

### Qualitative Studio Reviews (70%)

| Review Point | What's Evaluated |
|---|---|
| **Week 4 — Calculator + JS Fundamentals** | Working calculator app, JavaScript fluency, understanding of edge cases and state management. Can the student explain why `0.1 + 0.2 !== 0.3` and what to do about it? |
| **Week 8 — Registration System MVP** | Working registration flow, database integration, basic auth. Can the student walk through their code and explain every decision? Demo of the AI Audit Log so far. |
| **Week 12 — Testing + CI/CD Review** | Test coverage, CI/CD pipeline, code quality. Can the student show what their tests catch — and what they don't? Can they give CRC critique on a peer's test strategy? |
| **Week 15 — Final Studio Review + Demo Day** | Complete system, deployed and working. AI Audit Log defense. Can the student explain where they trusted AI and where they didn't — and why? |

Each review is a **conversation** between instructor and student, documented with:
- What the student demonstrated
- Feedback given
- Commitments for improvement
- Qualitative rating: Exceeds / Meets / Approaching / Not Yet

**Demo Day** (Week 15): Students present their registration system to peers and invited guests. This is the first Demo Day experience — smaller and lower-stakes than IS 425, but real practice at defending your work in public.

**Letter Grade Scale:** A: 90–100 | B+: 86–89 | B: 80–85 | C+: 76–79 | C: 70–75 | D: 60–69 | F: 0–59

*Final grades combine quiz scores (30%) and the instructor's holistic assessment across the four studio reviews (70%).*

## Signature Assessment: The AI Audit Log

The AI Audit Log is IS 118's signature artifact. For every meaningful AI interaction during development, students document:

- **What they asked**: the prompt or request
- **What AI produced**: the generated code or suggestion
- **What they did with it**: accepted, modified, or rejected
- **Why**: the judgment reasoning — what quality criteria were applied

The Audit Log is not a gotcha tool. It's a professional discipline. In enterprise settings, every consequential AI interaction will need a paper trail. Students who build this habit early will have a permanent competitive advantage.

## Key Deliverables

### Calculator Application (Weeks 2–4)
A fully functional calculator that teaches architectural thinking:
- Basic operations with proper state management
- Edge cases handled: divide by zero, overflow, chained operations
- Input validation (what happens when someone types "abc"?)
- At least one "the hard way" implementation where the student builds the logic without AI

### Workshop Registration System (Weeks 5–15)
A real, deployed product for the Center for Enterprise AI:
- **User-facing**: Browse workshops, register, receive confirmation, manage registrations
- **Admin-facing**: Create workshops, set capacity, view registrations, export data
- **Technical requirements**: RESTful API, database persistence, user authentication, session management, input validation, error handling
- **Security**: Password hashing, HTTPS, protection against common vulnerabilities (XSS, SQL injection, CSRF)
- **Testing**: Unit tests, integration tests, at least one end-to-end test
- **CI/CD**: Tests run on every push; deployment automated
- **Deployed**: Accessible via public URL

### AI Audit Log
Maintained throughout the semester, submitted as a structured document at Week 15.

### Context Pack v2
Building on v1 from IS 117:
- Architectural decisions and their reasoning
- Quality criteria used to evaluate AI output
- Known limitations and technical debt
- What I'd do differently with more time

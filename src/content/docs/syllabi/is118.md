## Course Description

Students build a real product — a **workshop registration system** for the Center for Enterprise AI — using JavaScript, server-side fundamentals, databases, APIs, and automated testing. This is not an abstract exercise. The system must handle user registration, session management, capacity limits, confirmation emails, and an admin dashboard. Real people will use it.

Along the way, students confront the central question of Professional Judgment: **"Just because AI can generate this code, should I ship it?"**

The answer requires understanding what the code does, what could go wrong, who gets hurt when it fails, and whether you'd stake your name on it. That's judgment — and no AI has it.

## Why Vocabulary Has Power

An LLM converts energy into intelligence — superhuman reading, writing, and deciding compressed into seconds. But the quality of that intelligence depends entirely on the context you provide. The same model that produces generic advice for a vague prompt produces expert-level analysis when you invoke the right names, concepts, and frameworks.

The mechanism is measurable. A vague prompt like "fix the code" costs 4 tokens and produces generic suggestions — the model distributes attention across every possible meaning of "fix." A precise prompt like "Refactor using the Repository pattern per Martin Fowler" costs 10 tokens but activates the exact knowledge cluster from *Patterns of Enterprise Application Architecture*. The vague version requires 4-5 rounds of back-and-forth to converge — thousands of total tokens. The precise version often nails it in one pass. Vocabulary doesn't just improve quality; it reduces total energy expenditure. The code parallel is exact: `"Ward Cunningham technical debt"` is an indexed lookup. `"That shortcut thing"` is a full-table scan.

When you say "Ward Cunningham technical debt" to an AI, you don't just get a definition — you invoke the metaphor's full context: financial debt as a model for software shortcuts, the difference between deliberate and accidental debt, the interest payments that accumulate when you don't refactor, and twenty years of industry debate about when debt is strategic and when it's negligence. When you say "Roy Fielding REST," you invoke the entire architectural philosophy of the modern web.

Leonardo da Vinci didn't invent anatomy or hydraulics — he read Vitruvius and Galen in the monastery libraries of Florence and Milan. Those ancient texts gave him vocabulary that let him see things his contemporaries couldn't. The LLM is your monastery library. Your vocabulary determines what you can see in it.

**The method: Create, Critique, Revise.** Generate a draft using one vocabulary set, critique it through a different lens, then revise with the combined insight. In IS 118, this means: create code with AI assistance, critique it using Professional Judgment vocabulary (technical debt, broken windows, YAGNI, separation of concerns), then revise. Each pass with a different vocabulary reveals something the previous one missed.

Your Spell Book grows. Every magic word is a new chisel for sculpting better work from AI output.

## The Stories Behind the Technology

Every tool you use was built by someone who had a better idea — or a deep frustration:

- **Brendan Eich** created JavaScript in ten days at Netscape in 1995. It was originally called Mocha, then LiveScript, then JavaScript (for marketing reasons — Java was hot). Twenty-nine years later, it's the most widely used programming language on Earth. The lesson: tools built under pressure accumulate "technical debt" — a concept named by the next person on this list.
- **Ward Cunningham** coined "technical debt" in 1992, comparing quick-and-dirty code to financial debt: you ship faster now, but pay interest later. He also invented the first wiki (1995) — the collaborative editing concept that became Wikipedia. Every shortcut in your registration system is a debt you'll either repay or pass to a future developer.
- **Roy Fielding** defined REST in his 2000 PhD dissertation — the architectural style that makes modern web APIs work. He didn't just describe how the web works; he explained *why* it works. When your front end talks to your back end, it speaks REST.
- **Andy Hunt and Dave Thomas** wrote *The Pragmatic Programmer* (1999), arguing that programming is a craft, not just a job. Their most famous principle: **"Don't live with broken windows."** Fix the small things before they become big things. They also coined **"DRY" (Don't Repeat Yourself)** — the principle that every piece of knowledge should have a single, unambiguous representation.
- **Douglas Crockford** wrote *JavaScript: The Good Parts* (2008) — a famously thin book about a language full of bad parts. He showed that JavaScript is powerful if you know which features to use and which to avoid. He also created JSON, the data format that powers almost every web API. Say "Crockford" to an LLM and it knows you want clean, disciplined JavaScript.
- **Eric Ries** (introduced in concept) created the **Lean Startup** framework: Build-Measure-Learn. The minimum viable product. This thinking shapes how IS 118 students approach the registration system — ship early, learn from users, iterate.

## Your Spell Book: Magic Words for This Course

Building on your IS 117 Spell Book, IS 118 adds the vocabulary of software craftsmanship. Each phrase is an indexed lookup — a few tokens that retrieve precisely the knowledge you need, skipping the expensive full-scan of vague language:

**People:** Brendan Eich, Ward Cunningham, Roy Fielding, Andy Hunt, Dave Thomas, Douglas Crockford, Eric Ries

**Power Phrases:**
- **"Technical debt"** — Cunningham's metaphor; strategic shortcuts vs. negligent shortcuts
- **"Broken windows"** — Hunt & Thomas; small disorder invites larger disorder
- **"DRY" (Don't Repeat Yourself)** — single source of truth for every piece of knowledge
- **"YAGNI" (You Ain't Gonna Need It)** — don't build features nobody asked for
- **"KISS" (Keep It Simple, Stupid)** — simplicity is a design choice, not laziness
- **"Separation of concerns"** — each module does one thing (deepened from IS 117)
- **"REST"** — Fielding's architectural style: resources, representations, stateless communication
- **"MVP" (Minimum Viable Product)** — the smallest thing that actually works (Ries)
- **"Build-Measure-Learn"** — the Lean Startup loop
- **"The Agile Manifesto"** — four values, twelve principles, Snowbird Utah 2001
- **"User stories"** — "As a [who], I want [what] so that [why]"
- **"CI/CD"** — continuous integration / continuous deployment; ship small, ship often
- **"Edge cases"** — what happens at the boundaries? Divide by zero, empty input, Unicode
- **"IEEE 754"** — why 0.1 + 0.2 does not equal 0.3 in JavaScript

Each phrase transforms your AI interactions from generic to professional.

## Foundations: Building with Numbers

IS 118 continues the foundational knowledge thread from IS 117, now applied to real programming:

- **How JavaScript handles numbers**: IEEE 754 floating point — why `0.1 + 0.2 !== 0.3` and what that means for handling money in your registration system. When to use integers (cents, not dollars).
- **The calculator as architecture teacher**: Students build a calculator app — not because calculators are exciting, but because a calculator forces you to think about state management, input validation, edge cases (divide by zero, overflow), and the gap between "it works for me" and "it works for everyone."
- **Boolean logic and conditionals**: How true/false, AND/OR/NOT map to real decisions in your code (can this user register? is this session full?).
- **Data representation**: JSON (Crockford's invention), form data, query strings — how information moves between browser and server.

## Why Professional Judgment?

AI can generate a login form, a database query, a test suite. It cannot know whether the login form leaks user data, whether the query will scale under load, or whether the test covers the case that will actually break in production.

Professional Judgment is the capacity to look at technically correct output and decide: is this *good enough to ship*? Does it handle edge cases? Does it fail gracefully? Would I want my name on it?

## Course Learning Outcomes

By the end of this course, students will be able to:

1. **Build** a full-stack web application with front-end UI, server-side logic, and database persistence (Create)
2. **Write** automated tests — unit, integration, and end-to-end — and explain what each level catches (Create)
3. **Implement** user authentication and session management with awareness of security implications (Apply)
4. **Design** RESTful APIs following Fielding's principles and handling errors gracefully (Create)
5. **Evaluate** AI-generated code against quality criteria: correctness, security, readability, maintainability (Evaluate)
6. **Set up** CI/CD pipelines that run tests automatically on every push (Apply)
7. **Produce** the AI Audit Log — a documented record of every AI interaction, what was accepted/modified/rejected, and why (Create)
8. **Apply** the CCR loop (Create-Critique-Revise) to concentrate AI intelligence through iterative refinement (Apply)
9. **Explain** foundational concepts: floating-point arithmetic, boolean logic, state management, data serialization (Understand)
10. **Construct** a Context Pack documenting architectural decisions, quality criteria, and known limitations (Create)

## How the Studio Works: The Coaching Model

IS 118 — like every studio in the spine — operates on a coaching philosophy. Instructors are **coaches and entertainment directors** who meet students where they are and create an environment where transformation happens through doing.

**The weekly rhythm (2 meetings/week):**

**Meeting 1 (e.g., Tuesday):**
1. **Canvas Quiz due before class** (auto-graded, 10-15 min) — covers last week's Magic Words and concepts
2. **Story of the Week** — the instructor tells the origin story of Brendan Eich's ten days, or Cunningham's debt metaphor, or Fielding's dissertation. Not a lecture — a story that gives vocabulary.
3. **Studio work** — hands on keyboards, building the registration system. Instructor circulates and coaches.

**Meeting 2 (e.g., Thursday):**
1. **Peer critique session** — students present progress, give and receive CRC feedback
2. **Code review practice** — applying Magic Words vocabulary to evaluate each other's code
3. **Pass/fail participation** — showed up, engaged, gave thoughtful critique = pass

**Why this works:** Students who feel safe take bigger risks, ask better questions, and produce better work. The studio is not a filter designed to fail people. It's a gym designed to make people stronger.

## Assessment

Assessment rewards engagement while reserving top grades for demonstrated excellence. **Consistent participation guarantees a passing grade.**

### Weekly Canvas Quizzes — 20%
- ~12 quizzes across the semester, auto-graded through Canvas
- Cover vocabulary and concepts: JavaScript fundamentals, database concepts, security vocabulary, software craft principles (DRY, YAGNI, broken windows, technical debt), REST, CI/CD, IEEE 754
- Lowest 2 scores dropped
- **Design intent:** Easy points for engaged students. Build the professional vocabulary.

### Studio Participation and Peer Critiques — 30%
- Graded **pass/fail per session** (~26 sessions across 2 meetings/week)
- Criteria: present, engaged, gave CRC feedback to peers, participated in discussion
- Up to 4 absences without penalty
- **Design intent:** Gets people into the room, talking, building the social climate.

### Final Project + Demo Day — 50%
- Workshop registration system + AI Audit Log, evaluated at Demo Day (Week 15)
- **Scored by an instructor panel** using a shared rubric:
  - **Technical completeness**: Does the system work? Auth, database, API, tests, CI/CD, deployed?
  - **Code quality**: Evidence of DRY, separation of concerns, Crockford-style disciplined JavaScript
  - **Professional Judgment evidence**: AI Audit Log quality — can the student explain every accept/modify/reject decision?
  - **Defense quality**: Can the student explain every decision and handle tough questions?
  - **Security posture**: Password hashing, input validation, OWASP awareness
- **Design intent:** Solid effort = B. Excellent work confidently defended = A.

**Letter Grade Scale:** A: 90-100 | B+: 86-89 | B: 80-85 | C+: 76-79 | C: 70-75 | D: 60-69 | F: 0-59

**How the math works:**
- All quizzes (18/20) + all sessions (30/30) + competent project (35/50) = **83 (B)**
- Aces quizzes (20/20) + all sessions (30/30) + outstanding work (45/50) = **95 (A)**
- OK quizzes (15/20) + most sessions (25/30) + minimal project (25/50) = **65 (D)**
- **The floor for an engaged student is a passing grade. The ceiling is earned.**

## Signature Assessment: The AI Audit Log

For every meaningful AI interaction during development, students document:

- **What they asked**: the prompt or request
- **What AI produced**: the generated code or suggestion
- **What they did with it**: accepted, modified, or rejected
- **Why**: the judgment reasoning — what quality criteria, what Magic Words (technical debt analysis? security review? YAGNI check?)

The Audit Log is not a gotcha tool. It's a professional discipline and a record of the CCR loop in action. In enterprise settings, every consequential AI interaction will need a paper trail.

## Key Deliverables

### Calculator Application (Weeks 2-4)
A fully functional calculator teaching architectural thinking:
- Basic operations with proper state management
- Edge cases: divide by zero, overflow, chained operations, IEEE 754 surprises
- Input validation (what happens when someone types "abc"?)
- At least one "the hard way" implementation without AI

### Workshop Registration System (Weeks 5-15)
A real, deployed product for the Center for Enterprise AI:
- **User-facing**: Browse workshops, register, receive confirmation, manage registrations
- **Admin-facing**: Create workshops, set capacity, view registrations, export data
- **Technical**: RESTful API (Fielding), database persistence, user auth, session management, input validation, error handling
- **Security**: Password hashing, HTTPS, XSS/SQL injection/CSRF protection
- **Testing**: Unit, integration, at least one end-to-end test
- **CI/CD**: Tests run on every push; deployment automated
- **Deployed**: Accessible via public URL

### AI Audit Log
Maintained throughout the semester, submitted as a structured document at Week 15. Evidence of Professional Judgment applied to every AI interaction.

### Context Pack v2
Building on v1 from IS 117:
- Architectural decisions and reasoning
- Quality criteria for evaluating AI output (using Spell Book vocabulary)
- Known limitations and technical debt (Cunningham's framework applied honestly)
- Spell Book growth — new magic words and how they changed AI output
